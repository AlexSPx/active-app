# Rust migration boundaries

This document records decisions and evidence. The release wire contract and fixture index are in [contracts/v1](../../contracts/v1/README.md); read them with [the source inventory](rust-contract-source-inventory.md). These decisions override older offline plans where they conflict.

| Concern               | Decision                                                                                                                                           | Consequence                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage and migration | Fresh Active server data, SQLite only. No Java/PostgreSQL account or data migration, no WorkOS credentials or sessions, and no Flyway history.     | Preserve phone data independently; connect/import it explicitly and resumably to the selected new instance/account. SQLite schema evolution is new server work, not Flyway migration.                                                                                                                                                                                               |
| Identity              | Self-hosted OIDC, provider selection and recovery proof deferred to ALE-114.                                                                       | No WorkOS endpoints. Bind credentials, local profiles, caches and queued jobs to both server instance and account; switching must fence in-flight work. Restore must preserve instance identity.                                                                                                                                                                                    |
| Streaks               | Client computes streaks, freezes and next-workout state; server persists versioned client snapshots.                                               | A snapshot is derived, replaceable client state, not canonical workout history or proof a workout occurred. It needs its own version and history/rules revision provenance. On stale history or snapshot conflict, retain local work, pull/merge history and recompute locally; never merge by taking the maximum count. No server streak engine or server-triggered recomputation. |
| Reminders             | Client owns scheduling, permissions and delivery on each device. Server persists versioned reminder preferences.                                   | No server scheduler, push tokens, Expo/APNs/FCM delivery or remote push registration. OS permission state, registration artifacts, device-specific scheduled notification identifiers and platform jobs remain local; restoring an account must not duplicate reminders. Web support is limited by browser capabilities and must be documented.                                     |
| Workout history       | Completed records and their original event chronology are canonical training history; deleting a template must not erase its historical snapshots. | Preserve original completion instant and timezone, exercise identity and displayed data. Upload time is not completion time. Backdated records require personal-best reconciliation. A history revision must change atomically with meaningful record changes so clients can recognize stale snapshots.                                                                             |
| Personal bests        | In scope separately from streaks.                                                                                                                  | Server handles personal-best/progression results in historical order, while offline training remains independent of server availability. ALE-78's server streak and reminder assumptions are superseded, not its chronology and personal-best concerns.                                                                                                                             |
| Exercise identity     | Stable dataset source keys map to instance-specific server IDs; retired identities remain available for history.                                   | Do not match ambiguous names or silently invent mappings. PR 30's `mappingComplete`, unresolved source/legacy IDs and retired source keys are readiness evidence, not an authorization to discard unresolved records.                                                                                                                                                               |
| Versions and retries  | Preserve ALE-68's stale-write protection, including dependent versions and recoverable drafts.                                                     | Existing queue freezes `request_payload` before dispatch, retries it with the same key, and only remaps/advances unsent payloads. An attempted request must not be modified under its key; a changed request requires a new operation/key.                                                                                                                                          |
| Legal                 | Existing client bundles legal text and has remote text endpoints.                                                                                  | The client bundles offline text; the server also serves instance-specific Markdown text.                                                                                                                                                                                                                                                                                            |

## Actual client compatibility evidence

`contracts/v1/client-parser-observations.json` and `apps/client/tests/sync/rustContractObservations.test.js` execute the existing Zod parsers, rather than a replacement schema. They show that a PR 30-style nullable catalog item is rejected and that accepted items lose `sourceKey`/`retired`; a record response without server `streakUpdate` and historical record with null `workoutId` are rejected. These are observations, not complete Rust success/error fixtures. Current `apiService` has optional versions and accepts empty delete acknowledgements; the new protocol and client migration must explicitly close those gaps.

`apps/client/tests/sync/SyncEngine.test.js` exercises persisted request freezing, lost responses, remapping, successor version advancement and conflict recovery. Those tests cover current queue behavior, not full wire compatibility. Historical imports also need completion time and timezone in the queued payload; the present `WorkoutRecordRequest` has only a timezone-free `startTime`.

## Release contract

The [contract directory](../../contracts/v1/README.md) contains the operation matrix and fixtures; the [wire contract](../../contracts/v1/wire-contract.md) specifies the rules and migration gates. The existing client remains incompatible with the deliberate changes identified there; the Rust server and client migration are follow-on work.
