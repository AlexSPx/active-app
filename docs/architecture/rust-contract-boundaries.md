# Rust migration boundaries (ALE-110, work in progress)

This document records decisions and evidence; it is **not yet a complete release wire contract**. Read it with [the source inventory](rust-contract-source-inventory.md). ALE-109 and ALE-110 override older offline plans where they conflict.

| Concern               | Decision                                                                                                                                           | Consequence                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage and migration | Fresh Active server data, SQLite only. No Java/PostgreSQL account or data migration, no WorkOS credentials or sessions, and no Flyway history.     | Preserve phone data independently; connect/import it explicitly and resumably to the selected new instance/account. SQLite schema evolution is new server work, not Flyway migration.                                                                                                                                                                                               |
| Identity              | Self-hosted OIDC, provider selection and recovery proof deferred to ALE-114.                                                                       | No WorkOS endpoints. Bind credentials, local profiles, caches and queued jobs to both server instance and account; switching must fence in-flight work. Restore must preserve instance identity.                                                                                                                                                                                    |
| Streaks               | Client computes streaks, freezes and next-workout state; server persists versioned client snapshots.                                               | A snapshot is derived, replaceable client state, not canonical workout history or proof a workout occurred. It needs its own version and history/rules revision provenance. On stale history or snapshot conflict, retain local work, pull/merge history and recompute locally; never merge by taking the maximum count. No server streak engine or server-triggered recomputation. |
| Reminders             | Client owns scheduling, permissions and delivery on each device. Server persists versioned reminder preferences.                                   | No server scheduler, push tokens, Expo/APNs/FCM delivery or remote push registration. A history revision must change atomically with meaningful record changes so clients can recognize stale snapshots.                                                                             |

## Actual client compatibility evidence

`contracts/ale-110/client-parser-observations.json` and `apps/client/tests/sync/rustContractObservations.test.js` execute the existing Zod parsers, rather than a replacement schema. They show that a PR 30-style nullable catalog item is rejected and that accepted items lose `sourceKey`/`retired`; a record response without server `streakUpdate` and historical record with null `workoutId` are rejected. These are observations, not complete Rust success/error fixtures. Current `apiService` has optional versions and accepts empty delete acknowledgements; the new protocol and client migration must explicitly close those gaps.

`apps/client/tests/sync/SyncEngine.test.js` exercises persisted request freezing, lost responses, remapping, successor version advancement and conflict recovery. Those tests cover current queue behavior, not full wire compatibility. Historical imports also need completion time and timezone in the queued payload; the present `WorkoutRecordRequest` has only a timezone-free `startTime`.

## Still required for acceptance

The release operation matrix, precise JSON request/response shapes and error/version/discovery/auth semantics, representative success and failure fixtures for every operation, and execution of those fixtures against actual parsers and queue payloads remain unfinished. In particular, versioned deletion and source-key mapping need complete fixtures, and snapshot conflict and preference ownership need precise wire representations. Do not treat this document as approval to implement an invented protocol.
