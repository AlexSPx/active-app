# ALE-114: SQLite OIDC investigation

**Status: decision pending; not release acceptance.** Pocket ID 2.19.2 is the leading candidate. The required passkey enrollment/recovery and actual Active native and web session proofs are incomplete, so this record does not select it for release. Rauthy has not been evaluated sufficiently and is not an approved fallback.

## Evidence collected on 2026-11-06

- [Pocket ID 2.19.2](https://github.com/pocket-id/pocket-id/releases/tag/v2.19.2), source tag `2b2750ed61e0016f4c15630322d15ca22143cdb6`, published 2026-11-02. The downloaded Linux amd64 release binary matched its published checksums file. It started with a disposable key, logged `provider=sqlite`, and created `data/pocket-id.db`, WAL and uploads; no PostgreSQL was used.
- Live discovery advertised code, S256, public token endpoint authentication (`none`), `offline_access`, refresh and end-session. It also advertises `plain`; Active must require S256.
- A browser submitted initial administrator signup and reached passkey setup. Passkey creation was skipped; this does **not** prove usable enrollment or passkey login. An operator CLI one-time recovery credential exchanged once with HTTP 200; its second exchange returned 401. Adding a replacement passkey and subsequently signing in were not tested.
- The admin UI accepted a public client with exact loopback and `activenext://auth/callback` redirects and a distinct API resource granted to that client. A browser on Linux, with the provider admin session already established, authorized the [loopback probe](../../deploy/auth-proof/README.md). The actual code + S256 exchange succeeded; the probe checked state, RS256 signature, issuer, ID-token audience and nonce, access-token signature, `at+jwt` type and API audience, rejected the ID token for that audience, rejected authorization-code replay, refreshed successfully and observed the refreshed token rejected after end-session. This is a protocol probe, not Active web login or a native system-browser callback.
- An immediate reuse of the original refresh token returned HTTP 200. The tagged source defines a **one-minute rotation grace period** (`backend/internal/oidc/store.go`); do not claim immediate replay detection. The follow-up below tested reuse after that grace. The test account's ID token had `email_verified: false`. The Active contract requires verified email for profile creation, so this account must not be accepted by Active.
- In separate loopback runs, an incorrect PKCE verifier returned HTTP 400; the probe rejected a deliberately mismatched nonce and a mismatched state, rejected the subsequent callback replay, and completed a new login after that failure. These are checks of the probe and provider, not the future Active client. Browser cancellation was not tested.
- This Linux host had no ADB devices; `emulator` and `xcrun` were unavailable. Docker Desktop daemon was unavailable and access to the system socket was denied. The binary was run directly; Compose configuration was validated but not started. No device or production credentials were used.

## Candidate and constraints

Pocket ID is passkey-led rather than an Active password database. Tagged source defaults open signup to disabled and supports administrator-issued signup links; operators may choose open signup separately. User-facing Active copy must distinguish a private invitation from open registration. The tagged source defaults email verification to disabled and does not automatically mark email verified. Configure and test verification with working SMTP, or use an independently verified administrative process; do not set `EMAILS_VERIFIED` merely to bypass the Active contract. Operator-assisted one-time recovery does not need SMTP; self-service emailed recovery does. Verify actual invite and email UX before promising it. Secure the initial setup endpoint until the first administrator is created. Operators should register multiple passkeys and keep a protected recovery path.

The tagged source includes custom API resources and user-delegated grants. The public [API guide](https://pocket-id.org/docs/guides/apis) displayed an **unreleased version** banner when checked; do not rely on it alone as version-specific evidence. Configure a distinct Active API resource and require its exact audience; never accept an ID token as an API bearer token. The tagged introspection handler restricts introspection to the issuing client, so a separate API credential cannot be assumed to introspect native tokens. Verify access-token type, signature, issuer, expiry, audience and subject at the resource server. A locally verified JWT can remain valid until expiry after provider logout; deletion of provider-side sessions is not immediate JWT revocation at the API. Discovery did not advertise a revocation endpoint. Define and test acceptable lifetimes and logout semantics.

The intended native registration is a public client with no secret, exact `activenext://auth/callback`, system browser, authorization code, S256, fresh unpredictable state and nonce, and OS-protected tokens. The path is a proposed exact registration, not yet an app callback implementation. Web needs a separate confidential server-side client and same-origin Secure, HttpOnly, SameSite session cookie with CSRF and Origin checks as required by [the wire contract](../../contracts/v1/wire-contract.md); its client secret stays server-side. Register exact web and post-logout URLs, no wildcards. Do not ship a client secret in Expo. The loopback probe is not this web session.

## Operator direction

The [disposable configuration](../../deploy/auth-proof/README.md) pins the release. For a real deployment, use a stable HTTPS issuer, one local persistent disk, secure first-admin bootstrap, and keep the encryption key outside the image and backed up separately. Preserve the entire provider data directory and issuer. The binary includes `export` and `import`; tagged export source includes embedded actor data. Test encrypted backup and restoration on a clean instance including users, signing keys, passkeys, client registrations, actor state and uploads. Stop the service for a filesystem snapshot; never copy only the main SQLite file while WAL is active. Rehearse upgrade on a restored copy and establish supported rollback before changing production. No PostgreSQL is required by the candidate configuration.

## Acceptance work still required

1. Complete passkey enrollment and subsequent login, invite/open-signup policy and verified-email flow; prove lost-passkey recovery through adding a new passkey and signing in, with SMTP where applicable.
2. Implement a disposable Active-compatible native and confidential server-side web client. On Android and iOS use the system browser and exact `activenext` callback; prove success, cancellation/retry, mismatched state/nonce, reused code, wrong verifier and redirect. On web prove the same-origin server session, CSRF checks and logout.
3. Test wrong-audience/type/issuer rejection by the actual Active API and its logout/revocation behavior. Record versions, devices, steps and results without credentials. Test backup/restore and upgrade with real accounts and passkeys.
4. Select a released provider only after those results meet the contract. If Pocket ID fails, evaluate another released provider and document any non-SQLite embedded store; do not introduce PostgreSQL implicitly. No WorkOS migration or phone-data changes are part of this investigation.

## Follow-up evidence (review 1)

The corrected 2026-11-06 direct-binary run used separate authorization grants. Code reuse immediately after exchange returned HTTP 400 `invalid_grant`. A separate grant refreshed twice, proving the first rotated refresh token worked; after end-session the second rotated token returned HTTP 400 `invalid_grant`. Another grant accepted an immediate reuse of the original refresh token and rejected it with HTTP 400 `invalid_grant` after 65 seconds. All requests were against 2.19.2 on localhost; no token values were retained.

The confidential web probe rejected the default unverified test email. For a positive session test only, the disposable SQLite row was manually marked verified; a real email verification was **not** performed. Browser login then succeeded, JavaScript could not read the HttpOnly session cookie, a missing CSRF token was rejected, refresh and local-session logout succeeded, and a subsequent refresh without the session was rejected. The server's end-session request did not include the provider browser cookie, so browser SSO logout and provider-cookie clearance remain unproven. The localhost cookie was not Secure; production HTTPS remains untested. This proves the probe's checks, not the finished Active web integration.

With the provider stopped, a filesystem snapshot was copied to a new directory. SQLite `integrity_check` returned `ok` for both copies; the restored copy contained one user and two clients, started on the same issuer and returned discovery. The provider `export` produced a ZIP that passed archive integrity. Neither actual imported-archive restore nor restored passkey login was tested. An empty SQLite instance initialized under 2.19.1 was stopped and started under 2.19.2, with discovery and SQLite integrity succeeding. This is an empty-instance upgrade smoke test, not proof of account/passkey upgrade or rollback. Commands are in the [proof guide](../../deploy/auth-proof/README.md).

The standalone Expo native proof bundles for Android and iOS, and its RSA JWK verification was checked on Node. Its disposable `jsrsasign` dependency is unmaintained; verification under Hermes and on either device has not been established. The browser control interface exposed no virtual-authenticator API; clicking Add Passkey did not complete enrollment. Invitation enrollment, verified-email delivery, replacement-passkey login, and actual native callback, cancellation and replay remain required. Pocket ID remains a candidate, not a release selection.

## Follow-up evidence (2026-11-08)

On Linux, the checksum-verified 2.19.2 release ran with SQLite and a new disposable database. Headless Chrome's WebAuthn virtual authenticator enrolled the first administrator's passkey. After discarding that authenticator, the operator generated a one-time access link, used it to register a replacement virtual passkey, cleared browser cookies, and signed in using the replacement. Reusing the recovery link showed “Token is invalid or expired.” This was repeated against a second clean database using the [reproducible script](../../deploy/auth-proof/passkey-proof.cjs). It proves the provider's local flow with simulated authenticators; it does not prove a physical authenticator or a native device flow. The one-time link remains a sensitive credential and the operator must independently establish the user's identity before issuing it.

With a separate disposable database, `UI_CONFIG_DISABLED=true`, `ALLOW_USER_SIGNUPS=open`, `REQUIRE_USER_EMAIL=true`, and `EMAIL_VERIFICATION=required`, an open-signup account registered a virtual passkey. Before verification the account page reported restricted access. Pocket ID delivered a verification message to a local SMTP sink; opening the decoded email link showed “Email Verified Successfully.” The sink proves message generation and the verification operation, not delivery to a real mailbox, production SMTP authentication/TLS, invite-only signup, or an OIDC ID token with `email_verified: true`. It used `SMTP_TLS=none` on loopback only. This does not demonstrate an independent administrative email-verification process, so SMTP remains required for the demonstrated path. Do not configure automatic verified emails to bypass verification.

An Android 15 emulator was available; it had WebView Shell but no Chrome or Google Play services. A separate Expo development-client debug APK built successfully with Gradle. The initially running emulator disconnected during the build; a restarted read-only API 35 emulator installed the proof APK and displayed its sign-in form through Metro. The image has no Chrome/custom-tabs provider or Google Play services, and no OIDC login, callback, cancellation, refresh or logout was exercised. iOS remains untested on this Linux machine. None of these results selects a provider: the missing native and confidential-web coverage, usable verified-email OIDC claim, and restored-account backup/upgrade evidence remain acceptance gates above.
