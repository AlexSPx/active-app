# Active API version 1 wire contract

`release-operations.json` is the operation and example index. Paths are relative to the discovered instance except the OIDC provider routes. Each entry has a success and error example. The JSON `request` is the HTTP body unless the method is GET or DELETE; those use the path/query. `queue` records the existing SyncEngine argument serialization, not necessarily the future HTTP body. Examples are illustrative; `request-contract.cjs` and `response-contract.cjs` are the authoritative Active schemas. Legal examples describe the text response as `{content, contentType}` for the fixture index; the wire body is the raw `content` with `Content-Type: text/markdown; charset=utf-8`. OIDC examples describe protocol responses; redirect `location` is the Location header, with no JSON body.

## Surface and decisions

The finite release surface is the operation index. `apiService.ts` supplies direct calls; `UserRepository` calls profile directly, `ExerciseRepository` calls search/logs, `LegalRepository` reads bundled text, and workout/routine repositories use local SQLite and queue mutations through `SyncEngine`. The eight existing queued method names and argument shapes are in the index. The index adds discovery, catalog, snapshot and preferences. Active routine absent returns 404 `NOT_FOUND`. Client legal text is the offline source; the server serves its own terms and privacy text for instance-specific review. A client must not claim acceptance merely from fetching it.

## Wire rules

All Active JSON uses camelCase and UTF-8. A field shown as null is nullable; omitted optional request fields mean unchanged on PATCH/PUT, while explicit null clears a nullable field. Required response fields appear even if null. Empty lists are `[]`. Unknown response fields must be ignored. IDs are opaque strings of 1 to 256 UTF-16 code units scoped to an instance; the exact values `.` and `..` are reserved because URL resolution treats them as path segments; owner-scoped resources and every reference must be checked against the authenticated account. Return 404 for absent or non-owned IDs without disclosing which. Catalog IDs are instance-specific; `sourceKey` is stable within `sourceDatasetVersion`. A complete catalog contains retired entries, `sourceMappings` with explicit `(datasetVersion, sourceKey, exerciseId)` mappings retained across dataset revisions, `mappingComplete`, `unresolvedSourceKeys`, and `unresolvedLegacyIds`; never upload a record with an unresolved identity as a different exercise. Search returns matching catalog items with source keys.

Versions and history revisions are nonnegative integers. New entities start at 1 and increment on each meaningful mutation. Updates require `baseVersion`; profile-affecting routine changes also require `profileBaseVersion`. Versioned deletes carry these as query parameters. Missing version is 400 `VALIDATION_ERROR`; stale versions are 409 `STALE_VERSION` with the current entity version. Routine deletion always checks the profile version; workout deletion follows the atomic transformation below and returns changed routine versions. Record deletion checks record version and returns the new history revision. Account deletion checks profile version and deletes only Active data for the owner, not the OIDC identity. Stale writes must not overwrite local drafts. Retry only after pulling, resolving and creating a new operation/key.

Workout deletion atomically converts every affected routine pattern entry from `WORKOUT` referencing the deleted ID to `REST` with `workoutId: null`. It preserves day indices, pattern length, start date, routine type and active selection; even a single-day routine becomes a one-day REST routine. Each affected routine increments once, regardless of the number of converted entries, and `routineVersions` lists every changed routine and its new version; unaffected routines and the profile version do not change. In the same transaction, historical records referencing the template retain their title, exercise snapshots and achievements, set `workoutId` to null and increment their record version; if any records changed, increment `historyRevision` once. If a snapshot exists, clear its `nextWorkoutId` and associated deadline when they reference the deleted workout, and remove that ID from `weeklyCompletedWorkoutIds`; increment the snapshot version once if these fields change. Its stored history revision remains the revision used to compute it, so a history change makes it stale and clients recompute it from canonical history. Other snapshot fields remain unchanged. The `transformation` fixture illustrates the routine and profile effects.

Every mutation requires `Idempotency-Key` (nonempty opaque UUID recommended). Scope the key by instance and account; atomically save method, normalized target, body hash, result status and body with the mutation. Identical retries replay the original result, including dependent versions; a reused key with different request returns 409 `IDEMPOTENCY_KEY_REUSED`. Retain results for at least 30 days after completion; clients must reconcile before retrying beyond retention. A queued request is frozen before first dispatch; only unsent requests may be remapped or advanced. Auth provider endpoints follow provider semantics instead.

Errors from Active use `{ "code": string, "message": string, "currentVersion": number | null }`. Common codes/statuses: 400 `VALIDATION_ERROR`, 401 `UNAUTHENTICATED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `STALE_VERSION` or `IDEMPOTENCY_KEY_REUSED`, 426 `INCOMPATIBLE_VERSION`, 429 `RATE_LIMITED`, 500 `INTERNAL_ERROR`. `currentVersion` is populated only for a known stale owned entity. Validation errors may include a `field` identifying the invalid input; messages never contain parser or database internals. Error text is informational, not control flow. The JSON index uses a representative 401 for authenticated Active operations; discovery and public legal use 500 `INTERNAL_ERROR`; OIDC errors use the provider's OAuth error representation.

Discovery is unauthenticated over HTTPS (localhost HTTP only for development). `instanceId` is a stable opaque instance identity restored with backups; `contractVersion` is `1`. Active requests send `X-Active-Contract-Version: 1`; unsupported versions return 426 before mutation. The issuer and endpoints must use HTTPS and match the trusted issuer's OIDC discovery. Native uses system browser, authorization code with PKCE, registered redirect, state and nonce validation, and OS secure credential storage. Web uses a same-origin backend session with Secure, HttpOnly, SameSite cookies, CSRF and Origin checks; tokens are not exposed to browser JavaScript. Neither tokens nor keys belong in URLs or logs. OIDC provider operations in the index are protocol examples and must be reconciled with the provider selected in ALE-114.

The Active server authenticates bearer credentials as access tokens intended for the Active API, never as OIDC ID tokens. It must validate the configured trusted issuer and Active API audience, token type and expiry, and either verify the signature using trusted issuer keys or use authenticated introspection and require an active, unexpired token with the same issuer and audience. Missing, invalid, expired, wrong-issuer, wrong-audience and ID tokens return 401 `UNAUTHENTICATED`; authorization failures for authenticated accounts return 403 `FORBIDDEN`, except absent or non-owned resource IDs return 404 `NOT_FOUND`. The immutable account key is `(issuer, subject)` from validated credentials; email is never an identity key or a reason to link accounts. Web sessions bind to that same key. ALE-114 selects and configures the provider without weakening these requirements.

Time instants are RFC 3339 UTC strings with `Z`; calendar dates are `YYYY-MM-DD`; schedule entries are local `HH:mm` in the preference timezone. `startTime` and `completedAt` are instants, and `completionTimezone` is the original IANA zone, retained even if profile timezone changes. Reject invalid zones and completion before start. Preserve chronological order by `(completedAt, id)` ascending for reconciliation; record list and logs return newest first by `(completedAt, id)`. Other lists use `(createdAt, id)` ascending, catalog by `sourceKey`, patterns by `dayIndex`, and exercise/set arrays preserve user order. Reps are nonnegative integer counts, weights are nonnegative kilograms, durations are nonnegative seconds; aligned set arrays must have equal lengths for their modality. One-rep max and volume are kilograms and kilogram-repetitions, respectively; set index is zero-based.

Routine types are `SEQUENTIAL` or `WEEKLY_COMPLETION`; day types are `WORKOUT` or `REST`, with `workoutId` null for rest and required for workout. Exercise level is `BEGINNER`, `INTERMEDIATE`, `EXPERT` or null; category is `STRENGTH`, `STRETCHING`, `PLYOMETRICS`, `STRONGMAN`, `POWERLIFTING`, `CARDIO`, `OLYMPIC_WEIGHTLIFTING` or null. Force is `PULL`, `PUSH`, `STATIC` or null; mechanic `COMPOUND`, `ISOLATION` or null. Equipment is `BODY_ONLY`, `MACHINE`, `OTHER`, `FOAM_ROLL`, `KETTLEBELLS`, `DUMBBELL`, `CABLE`, `BARBELL`, `BANDS`, `MEDICINE_BALL`, `EXERCISE_BALL`, `E_Z_CURL_BAR` or null. Muscle arrays use the dataset's uppercase names. Template replacement is complete when supplied. Template exercise notes are returned as nullable fields so they survive hydration and later edits. A deleted template leaves its record title and exercise snapshots intact and record `workoutId` becomes null.

For each exercise, retain Java master’s Epley estimate `weight * (1 + reps / 30)` and volume `sum(reps * weight)` over sets with positive reps and weight. No eligible sets yields null. The first set wins equal 1RM estimates; a record achieves a personal best only when strictly greater than all prior records in chronological order. Emit null achievement fields otherwise; recompute later achievements when history changes.

Completed records are canonical history. Create/delete increments `historyRevision` atomically and recomputes personal-best outcomes chronologically, including later records affected by a backdated change. Streak snapshots are replaceable client-derived state with their own version, `historyRevision` and `rulesVersion`; a write with an outdated history revision fails 409 `STALE_HISTORY`. Read `/api/history/revision` and pull history and recompute on conflict, never merge counts by maximum. Clients must bracket a full history pull with revision reads and retry if they differ, so the snapshot identifies the history actually used. Preferences are account-scoped desired schedule and timezone with their own version; actual permission, local notification IDs and scheduled OS jobs are per-device and never uploaded. Clients reconcile scheduling locally after restore or preference changes. No server push, token registration or scheduling.

## Migration gates

The current client parser rejects profile fixtures without the old `notificationPreferences`, record creation without `streakUpdate`, and nullable historical `workoutId`; it strips additional version/time fields. The exercise parser preserves catalog source identity and nullable exercise metadata. It also accepts optional versions and empty delete acknowledgements. `deleteWorkoutRecord` queue currently passes a bare ID, and record requests lack completion instant and timezone. Release requires updating parser, transport, repositories, queue persistence and migration together before targeting version 1; fixture checks are not a claim that today's client can consume every response. Profile, snapshot and preference writes need idempotency and conflict handling. Web session implementation and exact provider configuration remain ALE-114/115 work.

## Authoritative request contract

`request-contract.cjs` is the normative, executable Zod 4 schema for every Active operation's body, decoded path parameters and decoded query parameters. Its operation IDs correspond one-to-one to the index; an empty object means no parameters, and null means no body. Unknown fields and parameters are rejected. The schemas specify required fields, nullability, defaults and structural validation. Defaults apply only on creation or where explicitly stated in the schema; on updates omission leaves the field unchanged. Nullable nested measurements are replaced as a whole; both members are required when the object is supplied. Names and titles must contain a non-whitespace character and are stored exactly as supplied. Usernames are unique per instance case-insensitively; collisions return 409 `USERNAME_TAKEN`. Email and username are Active profile attributes; changing them does not change the OIDC account or authenticate a user. On first login the server creates a profile at version 1: the provider must supply a verified email; if it does not, authentication cannot create an Active profile and returns 403. The server initializes username to `user_` followed by a stable unique alphanumeric suffix (within 30 characters), firstName and lastName to `User`, timezone and measurements to null, and registrationCompleted to false. The client can then update these attributes. Registration completion is explicitly set by the client; it is not inferred from other fields. A profile update can clear timezone or measurements, but not email, username, names or registrationCompleted. No password or provider registration request exists in Active.

A routine requires a client-supplied startDate, a nonempty pattern of at most seven contiguous day indices starting at zero, and a workout reference for each WORKOUT day; REST requires null. Defaults are SEQUENTIAL, null description and inactive. A supplied pattern replaces the entire pattern. An explicit `active` on update requires profileBaseVersion even if false; on create it is required when active is true. Setting active false clears this routine only if it is currently active; setting true makes it active. All referenced workout IDs must belong to the account. GET of an absent snapshot or preferences singleton returns 404 `NOT_FOUND` without creating defaults. After that response, the client bootstraps it with PUT and `baseVersion: 0`; concurrent creation is subject to stale-version handling. A version of zero is reserved for creating the snapshot/preferences singleton when absent; entity updates/deletes require the current positive version. Lists of reps and weights align by index; durationSeconds is an independent list of timed sets. Omitted set arrays default to empty; all numbers must be finite. Schedules have unique local times. Dates must be real calendar dates, instants UTC with Z, and timezones valid IANA identifiers. Reject invalid requests with 400; never silently drop unknown fields. Query parameters must occur at most once; query versions are unsigned decimal integers converted to numbers before schema validation. IDs in path and query are percent-decoded once. Authenticated Active calls require a bearer token or the web session described above. Mutations additionally require the idempotency and version headers described above; other Active requests require the contract-version header except discovery. GET and DELETE have no body.

OIDC endpoints are provider protocol operations, not Active JSON. Authorization uses response_type=code, client_id, redirect_uri, scope including openid, state, nonce, code_challenge and code_challenge_method=S256; the provider validates its registered redirect and PKCE. Token and refresh requests are form-urlencoded with the fields illustrated in the index, using provider-required client authentication where applicable. The logout request uses the provider's discovered end-session endpoint and its registered redirect and required parameters. Provider-specific optional fields, token lifetimes, revocation, and errors remain governed by OIDC/OAuth and the chosen provider; ALE-114 must bind that configuration before release.

## Detached history and identity

Every record creation, including a normal completion and a phone import, supplies `workoutTitle` and each `exerciseName` as the original display snapshots. The server stores and returns them verbatim; it never replaces them with a current template or catalog label. `workoutId` is required but nullable: use null when the source template is absent or belongs to another instance. A non-null ID must be an owned live template. No template needs to be created to import history. Every exercise supplies an `identity` with both a dataset version and source key, or both a legacy namespace and legacy ID, or both pairs. Null marks an unavailable pair. The legacy namespace is a stable identifier of the original dataset or instance, never a display name. `exerciseId` is required but nullable. A non-null ID must identify the exact catalog identity; reject mismatches. For a source pair, resolution uses an exact `(sourceDatasetVersion, sourceKey)` mapping, including retired entries; for a legacy pair, only an explicit authoritative legacy mapping may resolve it. When both pairs are supplied, authoritative mappings must not disagree; reject a conflict with 400. No name matching or invented identity is allowed.

If no exact mapping exists, submit null `exerciseId` and retain the identity and label. The server accepts and returns the unresolved record, and stores it durably; it must not attribute it to another exercise. Unresolved exercises have null achievement fields and are excluded from per-exercise progression until an authoritative mapping exists. On adding a mapping, resolve matching stored identities transactionally, retain their snapshots and chronology, recompute affected personal bests chronologically, increment versions of records whose resolved identity or achievements change, and increment historyRevision once. Every record has a client-generated `clientRecordId`, stable across import retries and unique within the account. The server retains it with the record and enforces uniqueness for the lifetime of that account, including after idempotency expiry; a duplicate returns 409 `RECORD_ALREADY_EXISTS` without creating another record; deletion retains a clientRecordId tombstone until account deletion. Record lists include it so a client can reconcile an uncertain outcome. Clients must not reuse it for a different record. Record creation and idempotency apply identically to imports. Clients persist pending import jobs and their keys per instance/account; after a lost response retry the identical request, and after an uncertain result beyond key retention reconcile with the server before creating a new operation. The `detachedImport` fixture demonstrates a deleted template and an unresolved source identity.
