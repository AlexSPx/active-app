# Active Rust release contract, version 1

`release-operations.json` is the operation and example index. Paths are relative to the discovered instance except the OIDC provider routes. Each entry has a success and error example. The JSON `request` is the HTTP body unless the method is GET or DELETE; those use the path/query. `queue` records the existing SyncEngine argument serialization, not necessarily the future HTTP body. Examples are illustrative values, not exhaustive schemas. Legal examples describe the text response as `{content, contentType}` for the fixture index; the wire body is the raw `content` with `Content-Type: text/markdown; charset=utf-8`. OIDC examples describe protocol responses; redirect `location` is the Location header, with no JSON body.

## Surface and decisions

The finite release surface is the operation index. `apiService.ts` supplies direct calls; `UserRepository` calls profile directly, `ExerciseRepository` calls search/logs, `LegalRepository` reads bundled text, and workout/routine repositories use local SQLite and queue mutations through `SyncEngine`. The eight existing queued method names and argument shapes are in the index. The index adds discovery, catalog, snapshot and preferences. Active routine absent returns 404 `NOT_FOUND`. Client legal text is the offline source; the server serves its own terms and privacy text for instance-specific review. A client must not claim acceptance merely from fetching it.

## Wire rules

All Active JSON uses camelCase and UTF-8. A field shown as null is nullable; omitted optional request fields mean unchanged on PATCH/PUT, while explicit null clears a nullable field. Required response fields appear even if null. Empty lists are `[]`. Unknown response fields must be ignored. IDs are opaque strings scoped to an instance; owner-scoped resources and every reference must be checked against the authenticated account. Return 404 for absent or non-owned IDs without disclosing which. Catalog IDs are instance-specific; `sourceKey` is stable within `sourceDatasetVersion`. A complete catalog contains retired entries, `mappingComplete`, `unresolvedSourceKeys`, and `unresolvedLegacyIds`; never upload a record with an unresolved identity as a different exercise. Search returns matching catalog items with source keys.

Versions and history revisions are nonnegative integers. New entities start at 1 and increment on each meaningful mutation. Updates require `baseVersion`; profile-affecting routine changes also require `profileBaseVersion`. Versioned deletes carry these as query parameters. Missing version is 400 `VALIDATION_ERROR`; stale versions are 409 `STALE_VERSION` with the current entity version. Routine deletion always checks the profile version; workout deletion atomically removes references and returns changed routine versions. Record deletion checks record version and returns the new history revision. Account deletion checks profile version and deletes only Active data for the owner, not the OIDC identity. Stale writes must not overwrite local drafts. Retry only after pulling, resolving and creating a new operation/key.

Every mutation requires `Idempotency-Key` (nonempty opaque UUID recommended). Scope the key by instance and account; atomically save method, normalized target, body hash, result status and body with the mutation. Identical retries replay the original result, including dependent versions; a reused key with different request returns 409 `IDEMPOTENCY_KEY_REUSED`. Retain results for at least 30 days after completion; clients must reconcile before retrying beyond retention. A queued request is frozen before first dispatch; only unsent requests may be remapped or advanced. Auth provider endpoints follow provider semantics instead.

Errors from Active use `{ "code": string, "message": string, "currentVersion": number | null }`. Common codes/statuses: 400 `VALIDATION_ERROR`, 401 `UNAUTHENTICATED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `STALE_VERSION` or `IDEMPOTENCY_KEY_REUSED`, 426 `INCOMPATIBLE_VERSION`, 429 `RATE_LIMITED`, 500 `INTERNAL_ERROR`. `currentVersion` is populated only for a known stale owned entity. Error text is informational, not control flow. The JSON index uses a representative 401 for authenticated Active operations; discovery and public legal use 500 `INTERNAL_ERROR`; OIDC errors use the provider's OAuth error representation.

Discovery is unauthenticated over HTTPS (localhost HTTP only for development). `instanceId` is a stable opaque instance identity restored with backups; `contractVersion` is `1`. Active requests send `X-Active-Contract-Version: 1`; unsupported versions return 426 before mutation. The issuer and endpoints must use HTTPS and match the trusted issuer's OIDC discovery. Native uses system browser, authorization code with PKCE, registered redirect, state and nonce validation, and OS secure credential storage. Web uses a same-origin backend session with Secure, HttpOnly, SameSite cookies, CSRF and Origin checks; tokens are not exposed to browser JavaScript. Neither tokens nor keys belong in URLs or logs. OIDC provider operations in the index are protocol examples and must be reconciled with the provider selected in ALE-114.

Time instants are RFC 3339 UTC strings with `Z`; calendar dates are `YYYY-MM-DD`; schedule entries are local `HH:mm` in the preference timezone. `startTime` and `completedAt` are instants, and `completionTimezone` is the original IANA zone, retained even if profile timezone changes. Reject invalid zones and completion before start. Preserve chronological order by `(completedAt, id)` ascending for reconciliation; record list and logs return newest first by `(completedAt, id)`. Other lists use `(createdAt, id)` ascending, catalog by `sourceKey`, patterns by `dayIndex`, and exercise/set arrays preserve user order. Reps are nonnegative integer counts, weights are nonnegative kilograms, durations are nonnegative seconds; aligned set arrays must have equal lengths for their modality. One-rep max and volume are kilograms and kilogram-repetitions, respectively; set index is zero-based.

Routine types are `SEQUENTIAL` or `WEEKLY_COMPLETION`; day types are `WORKOUT` or `REST`, with `workoutId` null for rest and required for workout. Exercise level is `BEGINNER`, `INTERMEDIATE`, `EXPERT` or null; category is `STRENGTH`, `STRETCHING`, `PLYOMETRICS`, `STRONGMAN`, `POWERLIFTING`, `CARDIO`, `OLYMPIC_WEIGHTLIFTING` or null. Force is `PULL`, `PUSH`, `STATIC` or null; mechanic `COMPOUND`, `ISOLATION` or null. Equipment is `BODY_ONLY`, `MACHINE`, `OTHER`, `FOAM_ROLL`, `KETTLEBELLS`, `DUMBBELL`, `CABLE`, `BARBELL`, `BANDS`, `MEDICINE_BALL`, `EXERCISE_BALL`, `E_Z_CURL_BAR` or null. Muscle arrays use the dataset's uppercase names. Template replacement is complete when supplied. A deleted template leaves its record title and exercise snapshots intact and record `workoutId` becomes null.

For each exercise, retain Java master’s Epley estimate `weight * (1 + reps / 30)` and volume `sum(reps * weight)` over sets with positive reps and weight. No eligible sets yields null. The first set wins equal 1RM estimates; a record achieves a personal best only when strictly greater than all prior records in chronological order. Emit null achievement fields otherwise; recompute later achievements when history changes.

Completed records are canonical history. Create/delete increments `historyRevision` atomically and recomputes personal-best outcomes chronologically, including later records affected by a backdated change. Streak snapshots are replaceable client-derived state with their own version, `historyRevision` and `rulesVersion`; a write with an outdated history revision fails 409 `STALE_HISTORY`. Read `/api/history/revision` and pull history and recompute on conflict, never merge counts by maximum. Clients must bracket a full history pull with revision reads and retry if they differ, so the snapshot identifies the history actually used. Preferences are account-scoped desired schedule and timezone with their own version; actual permission, local notification IDs and scheduled OS jobs are per-device and never uploaded. Clients reconcile scheduling locally after restore or preference changes. No server push, token registration or scheduling.

## Migration gates

The current client parser rejects profile fixtures without the old `notificationPreferences`, record creation without `streakUpdate`, and nullable historical `workoutId`; it strips catalog identity and additional version/time fields. It also accepts optional versions and empty delete acknowledgements. `deleteWorkoutRecord` queue currently passes a bare ID, and record requests lack completion instant and timezone. Release requires updating parser, transport, repositories, queue persistence and migration together before targeting version 1; fixture checks are not a claim that today's client can consume every response. Profile, snapshot and preference writes need idempotency and conflict handling. Web session implementation and exact provider configuration remain ALE-114/115 work.
