# Profile integration

`profile_http::routes()` expects `auth::authenticate(&state, &headers, mutation)` to verify the bearer or session and enforce session CSRF for mutations. It returns a `VerifiedPrincipal`; client identity headers are never trusted. Authentication must not provision accounts. The profile GET endpoints provision on first verified connection using a verified email; mutations only resolve an existing issuer and subject.

PATCH, PUT and DELETE require one nonempty `Idempotency-Key`. Successful results and the mutation commit together under the SQLite writer lock. The key is scoped to the account; reuse with a different method, normalized target or typed JSON body returns 409 `IDEMPOTENCY_KEY_REUSED`. Successful retries replay the original JSON before checking versions. Errors do not create receipts. Receipts are retained until account deletion (at least the contract's 30 days).

Deletion atomically cascades owned data, identities, sessions and ordinary receipts. A separate permanent tombstone holds a SHA-256 digest of each deleted issuer/subject. For the identity that requested deletion it also retains the operation key, fingerprint and original acknowledgement, allowing exact bearer retries after deletion. The digest is pseudonymous and may be linkable to someone who already knows the provider identity; the acknowledgement contains the deleted opaque account ID. The same identity is permanently barred from provisioning again, including with an otherwise valid old token. A new account therefore requires a different provider identity; there is no automatic reactivation. Deletion also stores a narrowly scoped, hashed web replay proof in the same transaction. The original cookie, CSRF token and exact Origin can replay only the original DELETE until that proof expires; they cannot authenticate ordinary requests. After expiry, a fresh verified OIDC login for the deleted identity creates a recovery-only cookie without recreating the account. It can recover the same acknowledgement and can be logged out, but has no profile access. No provider or device data is deleted.

Client deletion retries use the original key and query directly, without a preceding profile GET, with a verified bearer or the scoped web recovery proof. Initialization plans must persist each request and key before dispatch and bind them to the instance and account. Local data erasure remains a separate explicit user action.

Settings → Self-hosted account connects through native PKCE or the same-origin web session. Native credentials and account-scoped operation plans are kept in SecureStore. Web session metadata and operation plans are stored in tab sessionStorage; provider tokens never enter browser storage. Initialization checkpoints and deletion plans are saved before dispatch and retained across uncertain outcomes. Native refresh is serialized and verifies the subject before replacing credentials. Instance discovery prevents sending a pending mutation to a replacement server. Disconnect and remote deletion do not erase local profiles or workouts; full workout synchronization remains a separate delivery.
